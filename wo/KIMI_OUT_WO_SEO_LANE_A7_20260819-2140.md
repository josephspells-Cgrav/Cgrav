• # ADVERSARIAL AUDIT — WO_SEO_LANE_A7_GLOSSARY_POUR.md

  ## VERDICT

  **Sound to execute: yes. Sound as a verification instrument: no.** A competent builder can start and finish this WO without guessing on anything fatal — the file targets, the term list, the voice laws, and the gates are all concrete, and the insurance-neutrality law is genuinely well-drafted. But the WO's own proof-of-success (§7) cannot detect three of the exact failure modes the WO exists to prevent: it never checks the sitemap (a stated success criterion, and one the WO itself admits is unprobed), never checks that pages contain bodies (200 + an h1 passes with empty content), and greps the index for slug *text* rather than working *links*. Meanwhile the I3 gate-extension exception opens both a silent-skip path and a tamper path on the one gate that matters most for a 31-page pour, and the WO flags the `storm-chaser` collision while missing the two larger ones (`recoverable-depreciation` vs two existing entries + an existing article; the flashing and vent clusters colliding with each other). Patch §7 and I3 before dispatch — it is a ~15-line change — and add differentiation spines for four term clusters. Everything else is rework-risk reduction.

  ## FINDINGS

  **F1 · HIGH · §7 oracle / §2 sitemap criterion — the sitemap has no oracle.**
  Hole: §2 makes sitemap membership a success criterion (137 → 168) and §1 admits the composition mechanism is *unprobed* ("report whether glossary terms auto-compose"). Yet §7's oracle is only "31 pages 200 + index lists 51." Sitemap membership appears nowhere in the oracle, the gates, or I1–I5 — the only guard is a self-reported "finding" in the build report.
  Failure scenario: glossary terms are composed into the sitemap through a mechanism that silently caps, filters, or reads a stale list (or the builder's conditional §3 edit is subtly wrong). All 31 pages return 200, the index greps 51/51, every gate is green, the report says "sitemap: not auto-composed, coverage added" — and `sitemap.xml` ships without the 31 URLs. Nothing fails. Discovery of 31 new answer-unit pages is left to organic crawl on the exact lane whose entire thesis is cheap organic rankings.
  Minimal fix: add to §7 — `curl localhost:3210/sitemap.xml | grep -o '/resources/glossary/[a-z0-9-]*' | sort -u | wc -l` must print **51**, and grep for each of the 31 new slugs individually. One line, zero judgment required.

  **F2 · HIGH · §7 oracle — content presence is never verified.**
  Hole: the oracle proves routing (200) and heading (term in h1). It never proves the page contains a `shortAnswer` or `body`. TypeScript cannot catch this — an empty string satisfies the `GlossaryTerm` type, and a page rendering h1 + empty sections passes typecheck, build, and the oracle.
  Failure scenario: a field-name or rendering mismatch (page component reads a field the builder populated differently, or a template regression on the branch) yields 31 pages that are technically live and essentially blank. Thin/empty pages on a production marketing site are a real ranking-quality liability, and the only backstop is self-reported word counts in the builder's own report table.
  Minimal fix: extend the oracle — for each of the 31 slugs, grep the rendered HTML for the first sentence of that entry's own `shortAnswer` (or enforce a rendered-page word floor, e.g. ≥300 words). Proof must be mechanical, not a self-reported table.

  **F3 · HIGH · §5 I3 + §9 — the gate exception has a silent-skip path and a tamper path.**
  Hole: three defects compound. (a) §8 says to report "the I3 gate-extension edit **if made**" — that phrasing makes the extension optional, so a builder can run `doorway-check` un-extended (hardcoded at 20), watch it pass trivially over a corpus that never included the new terms, and report I3 green. (b) The exception normalizes editing the gate file; nothing pins the threshold (0.40), n-gram size, or corpus paths — a builder stuck at 43% on `recoverable-depreciation` can nudge the threshold while "extending the list," and the only control is the builder's own prose description of "the exact edit." (c) The WO never says whether the gate edit is *committed* — committed, it collides with Lane M's merge; uncommitted, the branch's green I3 is unreproducible by any verifier checking out the branch.
  Failure scenario: the pairwise check over the 31 new pages — the single most important check in a 31-page pour, against a site whose gate exists because doorway pages are a known trap — is either never actually run or is run against a weakened gate, and the merge-time reconciliation with Lane M happens *after* a green report has already been believed.
  Minimal fix: three sentences in I3 — (1) the extension is **mandatory** unless the gate provably derives from `GLOSSARY_TERMS` (state the check: does the script import from `lib/articles/glossary.ts`); (2) the only permitted diff is adding slug strings to the GLOSSARY array — paste the verbatim `git diff` of the gate file into the report, threshold and tokenizer lines byte-identical; (3) the gate edit stays **uncommitted** on the branch (local-only), and the report states the pre-edit and post-edit gate results over the *existing* 20 to prove the gate's behavior didn't change.

  **F4 · MED · §2 term list — `recoverable-depreciation` is the biggest collision in the pour and is unflagged.**
  Hole: the WO carefully warns about `storm-chaser` (one existing blog post) but says nothing about `recoverable-depreciation`, which is definitionally *the difference between* two existing glossary entries (`actual-cash-value`, `replacement-cost-value`) and is almost certainly explained inline in the existing article `acv-vs-rcv-roof-insurance-claims`. A 250–350 word body on recoverable depreciation cannot avoid restating ACV and RCV mechanics — the 5-gram overlap is structural, not a style slip.
  Failure scenario: builder writes a perfectly voiced entry and hits >40% against two glossary entries and one article simultaneously; enters a rewrite doom-loop; eventually either ships marginal text or is tempted toward the F3 tamper path. Rework that one sentence of warning would have prevented.
  Minimal fix: give `recoverable-depreciation` the same treatment `storm-chaser` got: "read `acv-vs-rcv-roof-insurance-claims` and the ACV/RCV entries first; define via the *mechanics of collecting* the depreciation (documentation, completion proof, timelines), not by re-deriving ACV/RCV."

  **F5 · MED · §2 term list — `sub-fascia` vs existing `fascia`: cannibalization and overlap, cited as a virtue.**
  Hole: the WO's own justification — "/fascia already part-ranks for 'sub fascia' (1,000/mo)" — means Google has already assigned that query to `/fascia`. The SEO-standard move (strengthen the fascia entry) is banned by I1 (byte-identical). The WO never acknowledges the cannibalization tradeoff, and the two definitions ("finished board the gutters hang on" / "structural board beneath it") will share phrasing.
  Failure scenario: new `/sub-fascia` page splits link equity and relevance signals with `/fascia`; neither consolidates the query; the #26/#50 positions drift instead of improving. Simultaneously the pair is a 5-gram overlap candidate.
  Minimal fix: one line of differentiation spine (sub-fascia = structural framing lumber *behind* the fascia, rot/redecking-adjacent; cross-reference don't re-define fascia), and an explicit acceptance note that cannibalization risk was considered — even one sentence converts a silent tradeoff into a reviewed decision.

  **F6 · MED · §2 term list — four internal collision clusters get no differentiation spines.**
  Hole: the pour's worst pairwise-similarity risk is *among the 31 new entries themselves*, and the WO gives the builder no map: `step-flashing`/`counter-flashing`/`kick-out-flashing` (all "where roof meets vertical wall," all subtypes of the existing `flashing` exemplar) · `soffit-vent`/`gable-vent`/`turbine-vent`/`attic-baffles` (five ventilation pages sharing "intake/exhaust, cool the attic, prevent moisture") · `roof-decking`/`tear-off`/`re-decking` (two existing + one new, same job-site moment) · `architectural-shingles`/`three-tab-shingles` (defined against each other) · `drip-edge`/`gutter-apron` (near-variants). The gate *will* catch these — as red gates, after the writing is done.
  Failure scenario: builder writes all 31, runs the gate, gets a half-dozen red pairs, and must rewrite in a loop — or, worse, "differentiates" by hollowing entries into thin mush. Likely rework, zero launch danger.
  Minimal fix: one clause per cluster naming the axis of difference (step = wall intersection weave; counter = masonry overlap; kick-out = water diversion into gutter / soffit = intake; gable/turbine = exhaust; baffles = the channel that preserves intake / re-decking = the deck-replacement event during tear-off / gutter-apron = drip-edge variant that reaches into the gutter trough).

  **F7 · MED · §3 vs §4 — the conditional sitemap fix can trap the builder, and there is no escalation clause anywhere.**
  Hole: §3 authorizes editing "the one file the existing 20 use for sitemap membership" if auto-composition is absent — but §4 bans `app/**` unconditionally. If the composition point turns out to be `app/sitemap.ts` itself, the builder holds a must-fix and a never-touch on the same file. More generally, the WO (written for an isolated builder with no fleet context) contains **no STOP-and-escalate rule**: the term list is final ("do not drop"), the gate may not be weakened, existing entries are frozen — so a pair that cannot get under 40% after honest rewrites leaves zero legal moves.
  Failure scenario: builder hits the app/** contradiction or an unpassable pair, and — having no authorized exit — improvises: edits the forbidden file "minimally," or ships the >40% pair and hopes. Both are worse than a stall.
  Minimal fix: name the conditionally-editable sitemap file explicitly (or state "if the fix requires `app/**`, STOP and report — do not edit"), and add one line: "If any invariant cannot be satisfied honestly, STOP and report the blocker; never resolve a contradiction by improvising outside §3."

  **F8 · MED · §2 voice laws — `relatedMoneySlug` is forced where no natural target exists.**
  Hole: every entry must link a money page from a fixed set of five. For `xactimate`, `storm-chaser`, `recoverable-depreciation`, `roof-warranty` there is no genuinely-nearest service page — any pick is a relevance-stretched internal link on exactly the entries where the WO demands maximum neutrality.
  Failure scenario: 31 pages each foot with a commercial link; on the insurance-adjacent entries the link itself reads as a claim-funnel ("Xactimate is… → our roof replacement services"), undercutting the neutral-register law and adding low-quality internal-link patterns across a page cluster whose value is trust. Survivable, but self-inflicted.
  Minimal fix: either allow `relatedMoneySlug: null` for the named insurance terms, or designate the fallback explicitly (`roof-inspection` for all insurance-adjacent terms) so the choice is the author's, not the builder's guess.

  **F9 · MED · §1/§2 — the index page's data-drivenness is asserted for `[term]` but never probed for the index.**
  Hole: §4's rationale ("the [term] route renders from data") covers the detail route. The success criterion "listed on the glossary index" assumes `app/resources/glossary/page.tsx` also composes from `GLOSSARY_TERMS` — unverified, and the index is in `app/**` (never-touch) if it doesn't. A hardcoded count string ("20 terms…") or a paginated/limited render is invisible to every gate.
  Failure scenario: 31 pages live, sitemap correct, and the index silently shows 20 — or shows 51 under a heading that says 20 — with no authorized fix. The §7 grep-51/51 oracle would catch a total failure, but only *after* the pour is written.
  Minimal fix: extend the §1 probe: "READ `app/resources/glossary/page.tsx`; report whether the index composes from `GLOSSARY_TERMS`. If it does not, STOP and report" (reading `app/**` is already sanctioned by §1's sitemap instruction; touching is the ban).

  **F10 · MED · §2 insurance law — neutrality scope is too narrow.**
  Hole: the factual/neutral law names three terms. But `hail-bruising`, `wind-uplift`, and `storm-chaser` are insurance-adjacent: their natural encyclopedic drift is toward claims guidance ("document the bruising and file…", "if a storm chaser says your insurer will cover…"), and `roof-deductible` (existing exemplar for tone) is the entry most likely to be read alongside them.
  Failure scenario: a hail-bruising body slides into claim-outcome framing or deductible language — the exact NC-law exposure the WO legislates against — while technically complying because the term wasn't in the parenthetical.
  Minimal fix: extend the neutrality law's scope to "insurance-adjacent terms (`recoverable-depreciation`, `xactimate`, `roof-warranty`, `hail-bruising`, `wind-uplift`, `storm-chaser`)" — it costs six words.

  **F11 · LOW · §2 — display `term` strings are unpinned.** Only slugs are given; the builder guesses casing/hyphenation ("Three-Tab Shingles" vs "3-Tab Shingles"; "Sub-Fascia" vs "Sub-Fascia Board"; trademark casing "Xactimate"). The oracle is self-consistent (it greps for whatever the builder chose), so a bad guess passes everything. Fix: give each slug its exact display string in the list.

  **F12 · LOW · §2 — word bounds are soft where the report is hard.** `body: ~250-350` (tilde) vs `shortAnswer: 60-100` (hard), with a word-count table required in §8 but no counting method specified. Fix: make both bounds hard and name the counter (whitespace split).

  **F13 · LOW · §2 — array ordering and index order.** "sub-fascia first in priority" is ambiguous against "appended"; if the index renders array order, the pour yields 20 curated entries followed by an unsorted block. Fix: "append in listed order; the index renders array order and that is intended" (or specify sorted).

  **F14 · LOW · §5 I1 — formatter churn threatens byte-identical.** No instruction to avoid format-on-save / `prettier --write` on `glossary.ts`; one editor save can rewrite quoting/wrapping across the existing 20 and fail I1 through no fault of the content. Fix: one line — "do not run a formatter over the file; match existing formatting by hand."

  **F15 · LOW · §5 I5 — the `!` ban has no check.** I5 is an invariant with no gate and no oracle line; it is enforced only by builder diligence and the PLUS-JUDGE pass. Fix: one grep in the report (`grep -c '!'` over the 31 new entries must be 0). Cheap symmetry with I1's mechanical verification.

  ## ANSWERS

  **1. Coverage holes.** The WO specifies the *data* well and the *surroundings* thinly. Missing, in order of consequence: (a) a duplicate-concept map against the existing 20 — the builder is never told which new terms sit inside existing entries' blast radius (`recoverable-depreciation` ⊂ ACV+RCV; three flashing subtypes ⊂ `flashing`; `gutter-apron` ≈ `drip-edge`; the vent cluster ⊂ `ridge-vent`'s topic; `re-decking` between `roof-decking` and `tear-off`), so the gate becomes the discovery mechanism instead of a verifier; (b) display `term` strings — only slugs are pinned; (c) index-page composition — asserted for the detail route, never probed for the index, and the index is never-touch if hardcoded; (d) array ordering semantics — "sub-fascia first in priority" vs "appended" vs whatever order the index renders; (e) the sitemap-fix file's identity — conditionally authorized in §3 while `app/**` is unconditionally banned in §4; (f) an escalation clause — the list is final, the gate immovable, the existing entries frozen, and no legal exit exists if those three collide.

  **2. Underspecification sweep — every guess the builder must make.** Display strings and casing for 31 terms (incl. trademark casing) · insertion point and whether "first in priority" changes array order · per-term `relatedMoneySlug` with no worked examples and forced picks for terms with no natural target · whether 351 words fails "~250-350" · how to count words for the §8 table · which climate/number claims count as "generic"/"defensible" beyond the two examples · whether the sitemap fix file is the `lib/` registry or `app/sitemap.ts` · how to detect "Lane M's derived version is merged" from inside an isolated worktree · whether the I3 gate edit is committed · what "record the exact edit" means (prose vs verbatim diff) · whether the §8 report itself is committed and whether creating it violates ONLY-THESE-FILES (it must be created, but §3 doesn't list it).

  **3. The term list.** Duplicates-in-disguise: **`recoverable-depreciation`** is the standout — definitionally contained in two existing entries and one existing article, and unflagged (F4). **`sub-fascia`** collides with `fascia` by the WO's own evidence (F5). **`gutter-apron`** is a `drip-edge` variant; **`step-`/`counter-`/`kick-out-flashing`** are subtypes of the existing exemplar `flashing`; **`re-decking`** sits between `roof-decking` and `tear-off`. None of these are reasons to drop terms — all are reasons for one-line spines. Legal/compliance: the neutrality law is well-built for its three named terms; **`xactimate`** is a proprietary Verisk trademark — nominative definitional use is low-risk, but the WO gives no "no implied affiliation / describe don't evaluate" guidance, and trademark casing is unpinned (F11); **`roof-warranty`** carries a consistency risk the WO ignores — the glossary definition must not contradict the company's own warranty representations elsewhere on the site, and no instruction says to read them; the neutrality scope should extend to `hail-bruising`/`wind-uplift`/`storm-chaser` (F10). Homeowner-search fit: the list is strong overall; **`shingle-exposure`** is the weakest (contractor jargon — the exposed portion of a course is not something a homeowner googles; it will earn impressions only as an AI-citation unit); **`xactimate`** is mixed-audience (mostly contractor software, but homeowners who receive an estimate do search it — defensible); **`attic-baffles`** and **`rake-edge`** are low-volume but legitimate. No term on the list is a *never-search* bad enough to strike — and the list is final anyway; the fix for all of the above is guidance, not roster changes.

  **4. The I3 exception.** Letting the builder extend the gate's list locally is *directionally* sound — the hardcoded list genuinely is the defect, blocking the pour until Lane M lands would be pure serialization loss, and the orchestrator reconciles at merge. But as written it opens the "builder weakens the gate" cheat in **two** ways, not one: the tamper path (edit threshold/tokenizer while "extending the list," describe only the list change in the report) and the skip path (§8's "if made" makes the extension optional — run the gate at 20, pass trivially, report I3 green without ever checking the new terms). The commit-status ambiguity makes both worse. Minimal safeguard (F3): mandatory extension with a stated derivation check, verbatim `git diff` of the gate file in the report with threshold/tokenizer byte-identical, uncommitted-only, plus before/after runs over the existing 20 to prove gate behavior is unchanged. That is four lines of WO text to close the only cheat that touches the site's actual doorway-defense.

  **5. The oracle.** Yes — §7 can pass while the feature is broken, in three ways. (a) **Sitemap silently missing:** no sitemap check exists anywhere in oracle, gates, or invariants, despite being a stated success criterion with an admittedly unprobed mechanism (F1). (b) **Pages 200 but empty:** the type system guarantees the *field* exists, not that it has content; h1 + empty body passes everything (F2). (c) **Index lists slugs but links 404:** the oracle greps index HTML for slug *text*; an index rendering the right labels with wrong hrefs (`/glossary/` vs `/resources/glossary/`) greps 51/51 while every link is dead — only the reachability-check gate stands behind this, and the WO never states that it crawls from the glossary index. A fourth, softer hole: the oracle greps for whatever `term` string the builder invented, so a bad display string is invisible (F11). The fixes are all one-liners; the absence of (a) is the worst because the WO *knows* it doesn't know the sitemap mechanism and still didn't gate it.

  **6. THE ONE THING.** Harden §7 into a real proof: add the sitemap count-proof (51 glossary URLs in `sitemap.xml`, each new slug greppable), a per-page content proof (rendered HTML contains the entry's own `shortAnswer` first sentence), and href-level index greps (`href="/resources/glossary/<slug>"`, not bare slug). Why this over the I3 tightening or the collision spines: collisions surface as *red gates* — loud, fixable, the system working as designed — and Lane M's merge reconciliation is a partial backstop for I3. But the oracle holes are the place where the WO declares victory conditions (renders, listed, in sitemap) that its own verification *cannot detect failing*; a builder executing in perfect good faith can ship a broken pour with a fully green report, and the first human to notice would be Google. Convert the WO's success criteria from self-reported prose into three mechanical greps before dispatch — fifteen minutes of orchestrator time against the entire downside of the lane.
