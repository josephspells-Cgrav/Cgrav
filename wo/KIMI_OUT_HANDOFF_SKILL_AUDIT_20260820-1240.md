  **MAJOR**

  1. **Direct contradiction with the EPHEMERAL-STATE STAMP.** Line 45 (law dated 2026-07-27, with receipt): session-scoped live processes — "Monitors, sig-watches, dev servers, background tasks — **DIE WITH THE SESSION.**" and must be recorded as an Open Loop with a `RE-ARM` command, never as live state. New law, lines 101–102: "Detached OS processes (e.g. a backgrounded kimi builder) **SURVIVE the session — never assume they die with you; hand their PIDs … forward in §2 instead."** A backgrounded builder/dev server satisfies both descriptions. One law says treat it as dead and record a re-arm command; the other says treat it as alive and hand the PID forward as §2 live state. No criterion is given for which applies, and the stamp's receipt ("sig-watch Monitor armed" persisted while nothing was watching) is exactly the class of process the new law now says survives. A future session can cite either law to justify opposite behavior.

  2. **The new DoD gate has no ledger — violating the skill's own anti-skim hardening.** Lines 30–31: "each is backed by a **tool-derived artifact / written LEDGER**: the artifact is the proof, a claim is not." The DoD (line 57) now requires "outgoing session STOOD DOWN on every handed lane," but the 5 LEDGERS (lines 50–55) are unchanged — none covers stand-down, and no artifact is defined for it (a stand-down is a *negative* fact: "I didn't fire another builder," which a claim can fake trivially). Same gap on the read side: the "mandatory" liveness probe (3a) leaves no ledger entry, receipt, or verification artifact. "All 5 ledgers clean" can be fully met while the stand-down is merely asserted — the precise failure mode the hardening section exists to kill.

  3. **"Mid-run" is undefined and undetectable by the party who must act on it.** The probe is conditional everywhere: line 103 "mandatory when arriving mid-run," line 140 "mandatory if arriving mid-run," line 207 "If you are arriving mid-run." Nothing in the skill defines "mid-run," tells the successor how to determine it, or requires the *writer* to state it in the handoff. A fresh successor with zero context has every incentive and full license to conclude "not mid-run" and skip the entire protocol — the conditional is the skip hatch.

  4. **Missing failure mode: `list_sessions`/`send_message` unavailable.** The probe's only instruments are `mcp__ccd_session_mgmt__*` MCP tools. No fallback is specified if that server isn't registered, errors, or the successor's harness lacks it (this skill is used across agents — the workspace's own codex-executor has no Skill tool and a different toolset). As written, tool-unavailable silently degrades to "predecessor not found → proceed," which is indistinguishable from "predecessor dead." The protocol needs a defined degraded path (e.g., process/command-line check via `Get-CimInstance Win32_Process`, which line 109 already mentions but only for *post-incident* diagnosis, not as probe fallback).

  5. **Missing failure mode: send ≠ stood down.** Lines 105–107 require the successor to "SEND it a stand-down … AND post a lane-ownership claim … **before resuming the run.**" Nothing requires an acknowledgment, a re-probe (`isRunning` re-check after N minutes), or a timeout. A predecessor mid-turn will not even see the message until its turn ends — the receipt in lines 90–93 shows the rogue acting ~8 minutes *after* the successor started. The successor can send, claim, and resume into exactly the duel the section was written to prevent, in full compliance with the letter of the law.

  6. **Missing failure mode: two successors.** The protocol is framed strictly predecessor→successor. Nothing says to *check the blackboard for an existing ownership claim before posting one*, no claim format/heartbeat/ TTL is defined, and there is no tie-break if two live sessions both believe they own the lane (entirely plausible: user pastes the spin-up prompt into two windows, or a compact-resume and a fresh successor coexist). The dueling-orchestrator autopsy this section cites is itself a two-claimants-one-lane failure, and the fix doesn't address the symmetric case.

  7. **"Before resuming the run" contradicts "Orient then ASK — never auto-start."** Lines 106–107 ("before resuming the run"), 143 ("BEFORE resuming any run"), and 209 ("BEFORE resuming") all presume the successor *will resume a run* — but line 148–150 ("do NOT auto-start any task"), lines 225–227 ("Do NOT auto-start or auto-launch any task — picking the next task is <user>'s call"), and the final Principle (line 240: a handoff "hands over a ROLE, not a green light … never auto-starts") forbid exactly that unless the user picks the task. The spin-up prompt contains both instructions within the same block, so a fresh agent can read the PREDECESSOR LIVENESS paragraph as standing authorization to resume an in-flight run autonomously. The skill elsewhere (line 240) carefully distinguishes role-handoff from autonomous agent-launch; the new material blurs that line without saying which regime a mid-run arrival is.

  **VERDICT: AMEND-NEEDED**

  The core law (one lane, one orchestrator; stand down at emission; probe on arrival) is sound and well-motivated by the receipt, but: it contradicts the ephemeral-state stamp (finding 1) and Orient-then-ASK (finding 7), its gate bypasses the ledger discipline the skill elsewhere treats as the only thing that makes gates real (finding 2), its trigger condition is a skip hatch (finding 3), and three concrete failure modes — tool unavailable, message ignored, dueling successors — are unhandled (findings 4–6). Smallest sufficient amendments: reconcile the process-survival wording with the stamp, add a stand-down/probe artifact to the ledgers (or a 6th ledger), define "mid-run" with a detection rule or shift the declaration burden to the writer, specify the degraded-probe path and an ack/timeout/re-probe step, add a check-before-claim rule for lane ownership, and align "before resuming" with the never-auto-start principle.
