• ## VERDICT

  **Sound-to-execute: yes, but only after two amendments.** The two §Z rule shapes are correct for the corpus that exists today, the §B step-3 placement is right (spam dies before redirects and before the trailing-slash 308, giving the direct-410 the oracle demands), the dotless carve-out correctly protects `/sitemap.xml`, `/robots.txt`, and favicon-class assets, and the ceiling disclosure is mostly honest. The load-bearing defect is in the proof, not the rules: the negative control validates only *current sitemap paths* and *current `app/` route dirs*. It does not validate the third class of real URLs the middleware serves — legacy 301 / route-migration **sources** — and it proves nothing about the future, while the success criterion explicitly claims "no real page — current or plausibly-future — can ever match." F1 and F2 below are mandatory; F3–F6 are cheap. Neither mandatory fix requires redesign — they extend the guard and pin its persistence.

  ## FINDINGS

  **F1 — HIGH — The negative control omits LEGACY_301 and B-section migration source paths, and §Z fires before both.**
  Hole: §B pins the chain as §Z spam checks (step 3) → LEGACY_301 (step 4) → B-section migrations (step 5). A legacy redirect source is a *real URL with live SEO value*, but it is not in the sitemap and not an `app/` route directory — the guard's two enumerations structurally cannot see it. Failure scenario: the hacked-WP-era site has a legacy source like `/hail-damage-roof-repair-claims` (root, dotless, single-segment, 4 hyphens) that today 301s to a service page, carrying whatever link equity the old site had. §Z rule 1 matches it at step 3 → **410 instead of 301**, equity destroyed, chain-redirect debt erased in the worst possible way — and the guard reports green because the source was never in its corpus. Same hole exists for rule 2 if its scope is unpinned (see F3): any legacy source containing a whole keyword token dies. Minimal fix: enumerate **every LEGACY_301 source path and every B-section migration source path** into the negative control alongside the 137 sitemap paths and the `app/` root listing. This is a mechanical, five-minute addition to the guard and must gate deploy.

  **F2 — HIGH — Future-safety rests on an undocumented convention, not a mechanism; the "plausibly-future" success criterion is currently unprovable.**
  Hole: the guard as specified is a *one-time validation* of this change. §Z never states that the guard is committed as a permanent CI/build-time test, and never states the two invariants the rule silently imposes on all future work: (a) no root-level slug with ≥4 hyphens may ever ship, and (b) **no root-level dynamic segment (`app/[slug]/`) may ever exist** — a CMS-driven root blog or landing-page route would make every ≥4-hyphen post a 410, while the directory-enumeration control still passes because the literal string `[slug]` has zero hyphens. Failure scenario: 2027, a marketer (or a builder agent with no memory of this WO) ships `/spring-storm-roof-tune-up-special` or a root `[slug]` catch-all for landing pages. Pages return 410 from birth, get crawled and delisted, nobody connects it to a middleware rule written two years earlier. Silent, material SEO harm. Minimal fix (pick one, do both if cheap): (i) **preferred** — change rule 1's shape to *heuristic + build-generated allowlist*: 410 only if single-segment, dotless, ≥4 hyphens, **and the slug is not in a ROOT_ROUTE_MANIFEST generated from `app/` at build time**. Then "no future page can match" is mechanically true forever, not conventionally true today. (ii) minimum bar — commit the guard as a permanent test wired into CI/predeploy that fails *loudly* when any root route, redirect source, or root dynamic segment trips a §Z rule, plus a `//` comment at the rule naming the two invariants. Without one of these, strike "or plausibly-future" from the success criteria — as written, it's advertising.

  **F3 — MED — Rule 2's scope is unpinned, and the list contains one genuinely dual-use token.**
  Hole: rule 1 is explicitly scoped ("applies ONLY to single-segment root paths — namespaced paths are untouched"). Rule 2 says only "split the slug on hyphens" — *which slug* is undefined. A builder reading it as "any path's final segment" ships a different, broader rule than a builder reading it as "root single-segment like rule 1." Failure scenario: under the broad reading, a future legitimate page `/resources/ridge-vent-slots-explained` — `slots` is a real roofing term (ridge/soffit vent slots; also scheduling "time-slots") — returns 410 on a namespaced path, directly violating the WO's own "namespaced paths structurally unaffected" criterion. Minimal fix: pin rule 2 to the same scope as rule 1 (root-level, single-segment — which matches the recon: the spam is root-level), and add a `//` comment at `slots` recording that it is a known dual-use token kept deliberately because the scope restriction makes it safe. (`bally` is also a real place name — Bally, PA — irrelevant for a Charlotte NC site; note and move on.)

  **F4 — MED — Case handling unspecified; the stated ceiling doesn't cover case-variant spam.**
  Hole: neither §Z nor §B says the slug is lowercased before hyphen-counting or token-matching. If matching runs on the raw pathname, `/ONLINE-CASINOS-CURACAO-2026` and `/Chumba-Casino` evade rule 2 (token `Casinos` ≠ `casinos`), and short case-variants like `/Chumba-Casino` (1 hyphen) evade *both* rules → 404 decay instead of 410. This is not hypothetical: WordPress served these URLs 200 case-insensitively, so Google has had every incentive to index case-variant spam, and spam link-farms randomize case. The KNOWN CEILING paragraph does not disclose this residual. Minimal fix: lowercase the slug before both rules — provably safe because every real route is already lowercase (the negative control can assert this in one line) — and add oracle row `/ONLINE-CASINOS-CURACAO-2026` → 410 direct. If the builder probes and finds matching is already case-insensitive, say so in the report; either way the WO must state it.

  **F5 — LOW — The ceiling disclosure is honest on its two named classes but silently omits the nested-spam tail.**
  Hole: KNOWN CEILING names dotted paths and ≤3-hyphen no-keyword flat slugs. It does not mention *multi-segment* spam that matches no existing A2 pattern (`/author/`, `/category/`, `/blog/page/`, date archives are covered — arbitrary nested paths are not): e.g. `/promo/online-casino-bonus/` evades rule 1 (multi-segment) and, under the recommended F3 scope, rule 2 as well. Underscore/percent-delimited variants (`/online_casino_bonus`) are technically subsumed by the stated "≤3 hyphens" class, so that one is covered. Failure scenario: the report declares the "~5.5K flat-slug spam class" killed; GSC still shows a nested-path tail; the client's next audit asks why. Recon says root flat slugs merely *dominate* the 5.5K — domination is not exhaustion. Minimal fix: one sentence in KNOWN CEILING — "nested multi-segment spam paths not matching existing A2 patterns are out of scope and will 404; prevalence unknown from current recon." Honesty, not code.

  **F6 — LOW — Rule 2 has no *annotated* isolated positive control; the 9 quoted slugs are all rule-1-sufficient.**
  Hole: every one of the 9 positive-control slugs carries ≥4 hyphens, so rule 1 alone 410s them all — the guard could delete rule 2 entirely and stay green on its §Z-positive corpus. The de-facto rule-2 isolation row already exists in §G: `/online-casinos-curacao-2026` (3 hyphens, tokens `casinos` + `curacao`) — but only if no earlier A2 rule already 410s it; if an existing rule catches it, §Z's rule 2 ships with *zero* mechanical positive proof. Minimal fix: annotate each positive-control row with the rule(s) that catch it (the Polish `jednym-…` and `consecutive-avalanches-…` slugs are rule-1-only controls — good, keep them), and confirm `/online-casinos-curacao-2026` is caught by rule 2 *and no earlier rule*; if it is already covered, add one 3-hyphen keyword slug that only §Z rule 2 catches.

  ## ANSWERS

  **1. False-positive risk of the ≥4-hyphen rule.** Plausible future legitimate root slugs with 4+ hyphens are not edge cases, they are standard marketing output: `/roof-replacement-cost-charlotte-nc` (5), `/free-roof-inspection-storm-damage` (4), `/2026-spring-roof-tune-up-special` (5), `/insurance-claim-denial-help-guide` (4), `/metal-vs-shingle-roof-cost-comparison` (5), `/emergency-roof-tarp-service-after-storm` (5). The 2-hyphen ceiling of the current route table gives the rule only a one-hyphen margin over a slug as ordinary as `/hail-damage-repair-cost` (3). The negative control as designed is **not sufficient**: it proves the present corpus only, says nothing about redirect sources (F1), nothing about persistence (F2), and is blind to a future root `[slug]` dynamic segment (F2). The rule needs a different shape or a perpetual guard — build-generated root-route allowlist exemption preferred, permanent CI guard as the floor. With either amendment the rule is sound; without both it is a time bomb with a good alibi.

  **2. False-positive risk of the keyword-token list.** Checked token by token as a *whole hyphen-token* in plausible roofing/home-services slugs. `casino(s)`, `gambling/gamble/gambler`, `jackpot(s)`, `roulette`, `blackjack`, `poker`, `betting`, `wager/wagering`, `bookmaker`, `chumba`, `melbet`, `pinco`, `aviator`, `curacao`, `igt`, `spielautomaten`, `spieleliste`, `kasyno`: clean — no plausible legitimate use. `spins`: clean. **`slots`: real risk** — ridge-vent and soffit-vent slots, plus scheduling "time-slots"; survivable only if rule 2 is scoped root-only per F3, since legit uses will live on namespaced pages. **`bally`: marginal** — a real Pennsylvania borough name; irrelevant to this site's market but proves the list needs a maintenance note, not blind trust. The `storm` exclusion warning is correct and load-bearing — keep it verbatim in the code comment. Net: list approved *conditional on* the F3 scope pin; with the scope pin, residual risk is one commented token.

  **3. Missed sub-classes and ceiling honesty.** Missed: (a) dotted spam — **disclosed**, correct; (b) root flat slugs ≤3 hyphens, no keyword — **disclosed**, correct call as decay class; (c) underscore/percent-delimited flat spam — technically inside disclosure (b), acceptable; (d) **case-variant spam — undisclosed**, fixed for a line of code by F4; (e) **nested multi-segment spam outside existing A2 patterns — undisclosed**, F5. The ceiling statement is honest about what it names and incomplete by two classes. "Dominated by root-level flat slugs" in recon means a residual tail exists by construction; the report must say so or the next audit will.

  **4. Interaction bugs at §B step 3.** The ordering is *correct* for §Z's goal: normalization first means `/slug/` and `/slug//` 410 directly (matching oracle rows), query strings never reach the matcher, and root `/` is unreachable by both rules (0 hyphens, empty token list). Three real defects live at the seams: (i) §Z running before LEGACY_301 and B-section migrations is exactly why F1 bites — redirect sources must join the negative control; (ii) case handling is unpinned at the normalization step (F4) — normalization should lower-case the *match copy* of the path while leaving the redirect/Location copy untouched; (iii) the dotless test must run on the *raw* normalized path, which it does — and that is what saves `/sitemap.xml/` (normalized → dotted → excluded → falls through to the 308-fix row in §G rather than dying 410). The `%2F` oracle row is safe under both branches: decoded → trailing slash → rule 1/2 fire; undecoded → token `casinos` still fires. No earlier-rule breakage found from these three sections.

  **5. THE ONE THING for §Z.** The guard proves **today**, the success criterion claims **forever**, and nothing in §Z closes that gap. One amendment closes it: make the negative control **perpetual and complete** — a committed build/CI check over sitemap paths + root `app/` dirs + **all redirect sources** (F1) + a loud failure on any future root route or root dynamic segment that trips a §Z rule (F2), or equivalently regenerate a root-route allowlist at build time and exempt it in rule 1. Until then, §Z's central promise — "no real page, current or plausibly-future, can ever match" — is a convention wearing a proof's clothing.
