  ## VERDICT

  **REVISE BEFORE BUILD — do not implement as written.** The plan has the right skeleton (allowlist, hard guards, skip-step-0 instinct, two-phase confirm) and the pause-toggle discovery is genuine and valuable. But as written it **cannot meet its own success criteria 2 and 4**, it treats "impossible" as a vibe rather than an enforced invariant, it re-validates nothing at confirm time, and — worst sequencing call — it takes a **live, currently-biting customer-protection defect** (P5) hostage to a feature rollout with a sandbox gate in front of it. The operator told the system this morning "protect this woman from outreach." The system is not honoring that *right now*, while paid ads are live. That fix ships today, standalone. The verb ships after the holes below are closed.

  Zero findings is correct sometimes. This is not one of those times.

  ---

  ## FINDINGS

  **F1 · HIGH (launch-blocking) — "Impossible to double-enroll" is enforced by nothing.** Guard 1 is an application-level check-then-act: SELECT active run, then INSERT. The plan never mentions a database constraint. Concrete races: (a) preview at 14:00, confirm at 14:07 — a system trigger or the speed-to-lead intake path enrolls the contact in between; (b) the model retries `confirm:true` (Slack re-delivery, double "yes") and inserts twice; (c) two operators confirm within seconds. Any of these → two live ladders texting a real homeowner. With live ads and TCPA exposure, that is material harm, and criterion 2 says IMPOSSIBLE. **Fix:** partial unique index on `cadence_runs` over the enrollment key WHERE status is active; the confirm path re-runs the guards and attempts the insert in one transaction, mapping a constraint violation to the friendly "already enrolled" refusal. The app-level guard becomes UX; the constraint becomes the truth.

  **F2 · HIGH — The dedupe dimension is unspecified and probably wrong.** Guard 1 checks "an ACTIVE run exists for this contact." Runs may be keyed by lead; contacts share phones (spouses). Concrete failure: operator starts a ladder for Jane; a system run for John is active; same household phone → one phone, two ladders, both "guarded." Suppression and consent are phone-level facts; enrollment uniqueness must be too. **Fix:** dedupe on the normalized E.164 of the resolved recipient, and state explicitly which statuses count as active (cancelled is obvious; completed/failed/paused-ish states are not).

  **F3 · HIGH — Possible head-on collision with auto-enrollment, unaddressed.** The brief confirms every existing caller of `startCadence` passes `skipFirstStep:true` because a dialer makes the t=0 call off the same event. If that caller is a new-lead intake hook, then **every fresh lead — the operator's exact primary use case ("we call them, no answer, start a ladder") — already has an active run**, and guard 1 refuses the most common request this verb will ever get. The operator then either gives up or cancels the healthy auto-run to start a manual one, destroying positional state for no benefit. **Fix:** verify whether intake auto-enrolls (one code read); if yes, define same-key semantics — "already running this ladder, at step N, next touch T — restart?" — instead of a flat refusal.

  **F4 · HIGH — Content honesty is defended at exactly one step of one key; the rest is hope.** P4 neutralizes step 0 of `new_lead_followup`. Nothing else. (a) No eligibility preconditions per key: the model can select `no_show` because the name sounds like "didn't show up on the call," and the customer receives "sorry we missed you at your appointment" for an appointment that never existed — a false message by criterion 4's own definition. (b) `proposal_chase` started against a lead with no sent proposal is the same shape. (c) Later steps of all three keys ("more steps after") are copy-unaudited for context-dependent claims. (d) The preview states the first-touch *time* but not the *message text*, so the operator — the last honest checkpoint — cannot eyeball what will be sent in his name. **Fix:** per-key preconditions (no_show requires an appointment with no_show status; proposal_chase requires a sent proposal; new_lead_followup states lead age in preview); include first-touch channel + actual copy in `action_summary`; audit every step of the three allowlisted keys for premise-bearing copy before launch.

  **F5 · HIGH — The pause fix is real, under-verified, mis-sequenced, and half-scoped.** The defect claim rests on a grep for one helper name. That misses: wrapper predicates (`shouldContact()` that calls it internally), direct reads of the underlying column in SQL, and the separate customer-facing SMS agent, which the plan never mentions — if that agent sends outbound follow-ups, the hole stays open after P5. Additionally, "check it in the cadence step firing path" protects future step-fires but does nothing for **already-queued outbox rows** — the woman paused this morning could have a message sitting in the outbox right now. And making pause a global kill-switch silently swallows service messages too: `appt_reminder` for a booked estimate is arguably not "outreach," and blocking it causes a missed appointment — harm in the opposite direction, currently undecided. **Fix:** (1) ship the pause kill-switch as a standalone hotfix *today*, decoupled from this feature; (2) verify by tracing the storage column, not the helper; (3) enforce at send time in the spine (or drain pending rows on pause), not only at step-fire; (4) write down the decision on service messages and update the UI copy to state what "paused" now means.

  **F6 · MED — Confirm-time is a vacuum.** The plan checks guards "before any preview is shown" and says nothing about the `confirm:true` call. Minutes later, state may have changed: the customer texted STOP, the owner paused her, consent was revoked, another run started. Confirm is also unbound — `confirm:true` is a bare boolean; after conversational drift ("actually, do John instead") the model can confirm a contact who was never previewed. **Fix:** preview issues a token binding (contact, key, args, first-touch time) with an expiry (~10 min); confirm requires the token, re-runs all four guards, recomputes the first-touch time, and re-previews if it moved.

  **F7 · MED — The VAPI call path's gates are assumed, not shown.** The outbox spine enforces suppression, consent, and the 8–8 window for *sends*. P5's need to add pause "in the cadence step firing path" implies call steps dispatch on a different path. If STOP, consent, and the calling window are SMS-outbox-only, then a customer who opts out mid-run stops getting texts but still gets the +48h phone call — the worst possible touch to leak. **Fix:** one code read establishing the dispatch path for cadence CALL steps and the dialer; centralize so every touch — call or text — passes the same gate set.

  **F8 · MED — Blanket `skipFirstStep:true` is a guess applied to three keys after auditing one.** It is correct for the stated semantic ("a human just tried and failed") and for `new_lead_followup`'s false step-0 line. It is wrong when: the lead never got a t=0 call (dialer outage, manual import, aged lead) and the immediate beat was the point; or when a key's step 0 isn't a false-premise t=0 message at all — skipping it may drop an intended touch or strand later copy that references it ("per my text earlier"). `deferFirstStep` exists and is never discussed. **Fix:** per-key skip/defer decision justified by step-0 copy, written into the plan.

  **F9 · MED — The preview's "exact wall-clock time" will lie unless it is window-aware.** Start a ladder at 19:30 ET; step 1 nominal = 23:30; the spine holds to 08:00 next day. If the preview computes nominal step time, it states 11:30 PM for a touch that fires at 8:00 AM — a false statement to the operator, and it also changes content tone (a "just checking back" landing 12 hours later than implied). **Fix:** preview time = nominal time passed through the same window-hold logic the spine uses, labeled ET.

  **F10 · MED — Mid-run semantics are unspecified.** Customer is paused or opts out on day 1 of a 5-day run: do pending steps skip (gap in sequence) or hold (late burst of stale "just checking back" messages on un-pause — F4's content problem again)? Does `cancel_cadence` purge already-queued outbox rows or only stop future step-fires? All three answers are currently whatever the implementing session guesses. **Fix:** pick skip-vs-hold per trigger (pause = skip, suppression = terminal for that run), and verify cancel drains queued sends.

  **F11 · LOW — P1's floor declaration is internally inconsistent with the schema.** Schema makes both `lead_id` and `contact_id` optional; the floor declaration names only `contact_id`. The cited trap (sibling verbs refused on every call) bit verbs that *required* `contact_id` without declaring it; this verb declares it but may be *called without it*. Unspecified: exactly-one-of validation, lead→contact resolution order, and which identifier the audit row records. **Fix:** require exactly one, resolve lead→contact before the floor check, record both.

  **F12 · LOW — Test plan is pinned at the happy-path layer and silent on environment.** P6's pins are fine as far as they go. Missing: confirm-time re-guard tests; double-confirm idempotency; cross-key active-run refusal; shared-phone refusal; window-hold preview accuracy; paused-mid-run behavior; auto-enroll collision (F3); model-in-the-loop key-selection and name-resolution tests. Environment unspecified: which database the sandbox writes to (real homeowners are in prod), which Slack channel it announces to, and — the big one — it asserts the `cadence_runs` row exists but never asserts **zero outbox rows and zero dial attempts**. Also, "dialing is blocked for 555 numbers" covers calls; nothing said about SMS, and only 555-0100–0199 is the reserved fictional range — any other 555 number can be a real person's phone. **Fix:** pin 555-01XX fixtures, run against non-prod or with outbox dry-run, assert the negative space.

  ## ANSWERS (1–9)

  **1. Coverage vs the 5 criteria.** C1 (one turn): at risk — name→ID resolution is unspecified (F-missing, see 8), and if intake auto-enrolls, the common case returns a refusal, not a preview (F3). C2 (impossible double-enroll): **not delivered** — app-level check only, no constraint, three concrete races (F1, F2). C3 (impossible to start at opted-out/no-consent/paused): partially — guards run at preview only, nothing at confirm (F6); paused customers are reachable *today* until P5 ships (F5); call-path gates unverified (F7). C4 (no false content): **not delivered beyond one step of one key** — no eligibility preconditions, later-step copy unaudited, preview omits the message text (F4, F8, F9). C5 (no regression): plausible but under-budgeted — P5 touches the dialer and the firing path (wide surface), and the required unique index will churn existing test fixtures; neither is priced in.

  **2. The guards.** Sequence order among the four is nearly irrelevant (all refuse); don't invent an ordering bug — there isn't one worth the name. What slips past: everything time-based. State changes between preview and confirm (STOP, pause, consent revocation, system enrollment, second operator) hit all four (F1, F6). A shared phone slips guard 1 (F2). A lead with no linked consent record is fail-undefined — the plan says "no consent → refuse" but never says what happens when the link itself is missing; that must fail closed. Guard 3's own rationale ("the outbox would drop the sends anyway") only covers SMS, which quietly admits the call path is a separate question (F7). The race that matters is TOCTOU, and the only real fix is constraint + transactional re-check at confirm.

  **3. The allowlist.** Right shape; exclusions correctly follow the money-is-UI-only law. Two problems. `new_lead_followup` is the riskiest possible member content-wise (first-day-flavored copy throughout) and it ships with the least copy audit (F4). And the exclusion the operator will bang on within a week is `appt_reminder`: "hey Alex, text him about tomorrow's estimate" is the same sentence shape as the verbatim ask. Excluding it is defensible; not deciding and documenting the answer now is not. Refusal messages for excluded keys should name the allowlist so the model can relay it instead of improvising.

  **4. skipFirstStep.** Correct for the stated semantic and for the known false line; wrong as an unaudited blanket. It is wrong when no t=0 call ever happened (dialer outage, manual import, aged lead — the run then waits 4h for a touch the operator thinks is immediate), and wrong for any key whose step 0 isn't a false-premise t=0 message (F8). What breaks: silently dropped intended touches, or later-step copy orphaned by its reference to a step that never fired. And whenever it's applied, the preview time must survive the 8–8 window hold or the preview itself becomes the next false statement (F9).

  **5. The pause defect.** Reasoning: sound in conclusion, fragile in method — one grep on one symbol proves the helper has one caller, not that the *flag* has one consumer; trace the column and wrappers, and check the separate customer-facing SMS agent, which the plan ignores entirely (F5). Global kill-switch: the right call — it matches the UI label and the operator's demonstrated mental model; anything narrower is a lie the UI tells. What breaks legitimately: service messages (`appt_reminder` for booked appointments) get swallowed unless someone explicitly decides otherwise — decide, document, update the UI copy. Same-shape suspects elsewhere in this codebase: suppression checked for SMS but maybe not VAPI calls (DNC); `cancel_cadence` vs already-queued outbox rows; consent scoped to texts vs calls; the 8–8 window applied to the outbox but maybe not the dialer; the definition of "active" run statuses. Each is a "label says more than it does" until one code read proves otherwise.

  **6. Confirm-time re-checks.** Re-run all four guards, no exceptions — every one of them guards state that can flip in minutes. Also: bind the confirm to the preview with an expiring token (contact + key + args + first-touch time), because `confirm:true` alone cannot distinguish "yes, that one" from "yes" after the conversation moved to a different person. Recompute the window-adjusted first-touch time; if it moved, show a fresh preview rather than confirming against a stale promise. Make confirm idempotent — retries must hit the unique constraint, not create run #2. Write the audit row at confirm, not at preview.

  **7. The sandbox.** A 555 fixture is safe only under three conditions the plan states none of: the number is in 555-0100–0199 (other 555 numbers are assignable and owned by real people), SMS is blocked for it (the brief attests only to *dialing* being blocked), and the run writes to a non-prod database or an outbox in dry-run. "Verify the row, then cancel" asserts the positive and never the negative — the test must assert zero outbox rows and zero dial attempts, and it must force-fire the scheduler rather than trusting that cancellation beat the +4h timer. What I'd test that the plan doesn't: confirm-time re-guards, double-confirm, cross-key active-run refusal, two contacts sharing a phone, window-hold preview time, pause mid-run, the auto-enroll collision (F3), and the model-in-the-loop behaviors — key selection and name disambiguation — since those are where false-premise messages actually originate (F4).

  **8. Underspecification sweep.** Every place the implementing session will guess: how a spoken name ("so-and-so") becomes a `lead_id`/`contact_id` — lookup tool, fuzzy match, duplicate-name disambiguation, and what identity proof the preview shows (name + phone + last activity) so the operator can catch a misresolution before confirming; exactly-one-of on the two ID params and lead→contact resolution order (F11); which run statuses count as active; the enrollment uniqueness dimension — contact, lead, or phone (F2); which consent field, and fail-closed behavior when the link is absent; per-key step-0 copy and skip vs defer (F8); window-adjusted preview time and explicit ET labeling (F9); skip-vs-hold for paused/suppressed mid-run steps (F10); whether pause blocks system cadences (F5); the VAPI dispatch path's gate set (F7); preview token + expiry (F6); invalid-key error text listing the allowlist; what `end_reason`/audit rows a manual start writes; migration plan for the unique index against existing duplicate actives, plus expected fixture churn in the 3,035 tests; whether the sandbox exercises the real model loop or direct invocation (F12).

  **9. THE ONE THING.** **Make double-enrollment impossible at the database, inside the confirm transaction.** Partial unique index on active `cadence_runs` over the normalized recipient phone; the `confirm:true` path re-runs all four guards and attempts the insert in one transaction, translating a constraint violation into the "already enrolled" refusal. This single change closes F1, F2, the retry race, and the confirm-time hole in F6 in one move, and it is the only change that converts criterion 2 from a promise into an invariant. Everything else is rework; this one is the difference between "we check" and "it cannot happen." (Sequencing note, said once and not counted as the one thing: the P5 pause fix does not wait for this feature — it ships today on its own. See F5.)
